# 请求改写规则

AxonHub 提供请求改写规则，允许按模型改写请求体中任意字段的值，在请求路由到渠道之前生效。这适用于客户端发送了底层模型或渠道不接受的非标准字段值的情况——例如客户端发送 `"reasoning_effort": "xhigh"`，而某渠道的模型只支持 `high`、`medium`、`low`。

## 概述

请求改写规则定义：

1. **适用的模型** —— 精确模型名或正则，匹配客户端发送的原始模型名。
2. **要改写的字段值** —— 一个或多个请求体字段，每个字段带一组 `当前值 → 新值` 映射。

请求到达时，系统按模型查找启用的规则，替换请求体中的映射字段值。

## 工作原理

改写规则是客户端请求经过的**第一道关卡**，是对原始客户端请求解耦的最外层 filter：

- 请求刚解析完成就执行，**在**模型映射、模型访问检查、渠道选择**之前**。
- 模型匹配按**客户端传过来的原始模型名**进行。
- 与 AxonHub 后续所有路由逻辑解耦——除非某条规则改写了 `model` 字段本身。

```
┌──────────────────┐
│   客户端请求     │  例如 {"model":"gpt-4o","reasoning_effort":"xhigh"}
└────────┬─────────┘
         │
         ▼
┌──────────────────────────────────────────────┐
│              请求改写规则                     │
│  1. 加载启用规则（缓存）                      │
│  2. 按客户端原始模型名匹配规则                │
│  3. 替换请求体中的映射字段值                  │
└────────┬─────────────────────────────────────┘
         │
         ▼
┌────────────────────────┐
│ API 密钥模型映射        │  （既有功能）
└────────┬───────────────┘
         │
         ▼
┌─────────────────┐
│  路由后的请求    │  例如 {"model":"gpt-4o","reasoning_effort":"high"}
└─────────────────┘
```

## 核心概念

### 规则结构

| 字段 | 类型 | 说明 |
|------|------|------|
| **名称** | 字符串 | 规则唯一标识（每个用户内唯一） |
| **描述** | 字符串 | 可选描述 |
| **模型匹配** | 字符串 | 精确模型名或正则，匹配客户端的原始模型名 |
| **状态** | 枚举 | `enabled`、`disabled` 或 `archived` |
| **字段映射** | 列表 | 每个被改写字段一项 |

### 字段映射

每个字段映射包含 `path`（请求体字段名）和一组值映射：

| 字段 | 说明 |
|------|------|
| **path** | 请求体字段，如 `reasoning_effort`、`temperature`、`service_tier` |
| **from** | 要匹配的当前值；空值匹配不存在/为空的字段 |
| **to** | 替换后的值；空值表示从请求中删除该字段 |

同一字段按列表顺序匹配，**首个命中的 `from` 生效**；未匹配的当前值原样保留。多条规则命中同一字段同一值时，ID 最小（最先创建）的规则生效。

### 模型匹配规则

模式匹配的是客户端发送的原始模型名——在 API 密钥模型映射、模型访问检查、渠道选择之前。

- 精确名称直接匹配：`gpt-4o`
- 含正则字符时按完整锚定正则编译：`gpt-.*`、`claude-.*-haiku.*`
- 单独的 `*` 匹配所有模型

如果规则改写了 `model` 字段本身，后续流程（模型访问检查、模型映射、渠道选择）都会基于改写后的值。

## 创建规则

### 管理界面

1. 在侧边栏进入 **改写规则**
2. 点击 **创建规则**
3. 配置规则：
   - 输入唯一 **名称**
   - 填写可选 **描述**
   - 设置 **模型匹配**（精确名或正则）
   - 添加一个或多个 **字段映射**：字段路径 + `当前值 → 新值` 对
4. 点击 **创建**
5. 通过状态开关启用规则

## 使用示例

### 示例 1：归一化非标准 reasoning_effort

客户端发送 `"reasoning_effort": "xhigh"`，但渠道模型只接受 `high`。

**规则：**
- 模型匹配：`gpt-4o`
- 字段 `reasoning_effort`：`xhigh → high`

**改写前：**
```json
{ "model": "gpt-4o", "reasoning_effort": "xhigh" }
```

**发往上游：**
```json
{ "model": "gpt-4o", "reasoning_effort": "high" }
```

### 示例 2：为某模型系列删除字段

某些渠道会拒绝未知字段，可对其匹配的所有模型删除：

- 模型匹配：`deepseek-.*`
- 字段 `service_tier`：`flex → *（空）*`

发往上游的请求中 `service_tier` 字段被删除。

### 示例 3：为某模型固定 temperature

- 模型匹配：`claude-.*`
- 字段 `temperature`：`0.9 → 0.5`

所有发往 Claude 模型的请求都会把 `temperature` 固定为 `0.5`。

## 规则管理

### 状态管理

| 状态 | 说明 |
|------|------|
| **enabled** | 规则生效，应用于请求 |
| **disabled** | 规则停用，可重新启用 |
| **archived** | 规则已归档（软删除），列表隐藏 |

### 批量操作

- 在表格中选择多个规则后，可 **批量启用** / **批量停用** / **批量删除**。

### 缓存行为

启用的规则缓存在内存中以保证性能：

- 启用规则索引每 30 秒刷新
- 规则的增删改会触发异步缓存刷新
- 模型模式编译结果单独缓存

## 最佳实践

1. **优先使用精确模型名** —— 成本最低、语义最明确。
2. **匹配的是客户端的原始模型名** —— 规则运行在 API 密钥模型映射之前，用客户端实际发送的名字。
3. **明确预期的 `from` 值** —— 未匹配的值会原样透传，`from` 写错会静默不生效。
4. **保持映射精简** —— 每条规则都会给请求增加一次字段扫描。

## 常见问题

### 问：规则为什么不生效？

依次检查：

1. 规则是否 **enabled**？
2. **模型匹配** 是否命中客户端发送的模型名？（是客户端原始模型名，而非任何 API 密钥模型映射之后的名称。）
3. 请求中是否真的包含该字段，且当前值与 `from` 完全一致？（精确匹配，区分大小写。）

### 问：多条规则命中同一字段同一值时会怎样？

ID 最小（最先创建）的规则对该值生效。

### 问：能改写嵌套字段吗？

字段路径使用请求体顶层字段名（如 `reasoning_effort`）。已知统一请求模型中的字段直接改写到内部请求，所有出站 API 格式都会生效；其它顶层字段则直接修补客户端原始请求体。

### 问：改写会影响客户端看到的内容或日志吗？

改写发生在路由与记录日志之前。请求日志与 trace 记录的是改写后的值，body 透传的渠道也会发送改写后的 body。
